# 新機能・改善の流れ（部長が使う）

依頼: $ARGUMENTS

各工程の終わりに、担当の課長が docs/00_status/board.md を更新します。
同じ工程の手戻りが3回を超えたら、/escalate で社長に判断を仰ぎます。

## 1. 受付
- 依頼を1文に要約する。Issue番号なら `gh issue view <番号>` で読む。
- main を最新にして作業ブランチを作る：`git switch main && git pull && git switch -c feat/<短い英語名>`
- 社長指示Issueなら「受け付けました。進め方：…」とコメントする。

## 2. 研究（必要なときだけ）
- 新しいライブラリや技術が必要そうなら、研究課長（app-research-kacho）に調査と推奨を依頼する。

## 3. 要件定義
- 要件定義課長（app-req-kacho）に要件定義書（REQ）の作成を依頼し、approved を受け取る。
- 次のどれかに当たれば /escalate で社長判断にし、返答が来るまで工程4以降は止める：
  新機能の採否、外部仕様（使い方・出力）の大きな変更、機能の削除、共通指標仕様の変更、費用・ライセンス。

## 4. 設計
- 設計課長（app-design-kacho）に、REQ の番号を渡して基本設計（BD）→詳細設計（DD）を依頼する。設計課長のレビューで approved になるまで、課の中で手戻りする。
- 要件の不足が見つかったら、指摘を添えて工程3に戻す。

## 5. リファクタリング（DD に前提として書かれていれば）
- /refactor-pipeline を先に回す。

## 6. 開発
- 開発課長（app-dev-kacho）に、DD の番号を渡して実装を依頼する。Model・ViewModel・View係が実装し、テストとテスト仕様書（TS）を書く。開発課長のレビューと速いテスト（python -m unittest discover -s tests）が通るまで、課の中で手戻りする。
- 設計の不足が見つかったら、指摘を添えて工程4に戻す。

## 7. 品質保証
- 品質保証課長（app-qa-kacho）に、TS の番号を渡してテストを依頼する。不合格なら、失敗したケースを添えて工程6に戻す。
- 保守運用書の更新が必要なら、品質保証課の保守運用書係が更新する。

## 8. PR
- `git push -u origin <ブランチ>` の後、`gh pr create` でPRを作る。本文に：要約、REQ / BD / DD / TS / QA の番号、変更点、テスト結果、社長判断のIssue番号（あれば）。

## 9. マージの判断
- バグ修正・リファクタリング・書類だけの変更：部長がマージしてよい（`gh pr merge --squash --delete-branch`）。
- 新機能・使い方の大きな変更・共通指標仕様の変更：判断待ちIssueで社長の承認を得てからマージする。
- リリース（版数の更新・利用者への配布）：常に社長の承認が必要。

## 10. 後片付け
- 要件定義課の現状仕様係に、spec-current.md の更新を依頼する。
- 社長指示Issueに結果をコメントしてクローズする。社長に結論から短く報告する。
